# Redis

NMOCore uses [Redis Stack](https://redis.io/docs/stack/) for three purposes: response caching, full-text search (RediSearch), and shopping cart state.

## Connection

A single Redis connection is created at application startup in `app.py`:

```python
r = redis.Redis(host=cfg.redishost, port=6379, db=0)
```

The hostname defaults to `cache` (the Docker service name) and can be overridden with the `REDIS_HOST` environment variable.

## Docker Configuration

The `cache` service runs `redis/redis-stack-server` with these settings (in `docker-compose.yml`):

| Setting | Value | Purpose |
| --- | --- | --- |
| `appendonly` | yes | Append-only file persistence |
| `maxmemory` | 4gb | Memory limit |
| `maxmemory-policy` | allkeys-lru | Evict least-recently-used keys when full |
| `REDISEARCH_ARGS` | MAXSEARCHRESULTS -1 | No cap on search result count |

Redis is not exposed outside the Docker network. Only the FastAPI container connects to it.

## Key Namespaces

All Redis keys used by the application:

| Key Pattern | Type | TTL | Purpose |
| --- | --- | --- | --- |
| `quickstats` | String (JSON) | 24h | Cached quickstats response |
| `{hash}` (numeric) | String (JSON or pickle) | 24h | Cached endpoint responses (browse, neuron, metavals, chartcount) |
| `{hash}` (from search) | String (pickle) | ~5.8 days | Cached search results |
| `{idlistkey}` (numeric) | String (pickle) | 24h or ~5.8 days | Neuron ID lists for cross-endpoint chaining |
| `nmo_kw:{id}` | Hash | none | RediSearch document (title + body fields) |
| `nmo_idx` | RediSearch Index | none | Full-text search index |
| `cart:{uuid}` | Set | 24h | Shopping cart contents (neuron names) |
| `cart:{uuid}:meta` | String | 24h | Cart existence marker (value "1") |

## Response Caching

Most read endpoints cache their responses in Redis to avoid repeated database queries.

### How it works

1. A cache key is generated by hashing the request parameters: `hash(frozenset(params))`
2. On cache hit, the stored value is returned directly (either `json.loads()` or `pickle.loads()`)
3. On cache miss, the database is queried, the result is serialized and stored with a TTL

### Serialization

Two serialization formats are used depending on the data:

- **JSON** (`json.dumps` / `json.loads`): Used for simple responses like quickstats, browse trees, metavals, chartcount. These are plain dicts/lists that serialize cleanly to JSON.
- **Pickle** (`pickle.dumps` / `pickle.loads`): Used for complex responses like neuron query results and search results. These contain Pydantic model instances and pagination metadata that don't serialize to JSON easily.

### TTLs

| Endpoint | TTL | Notes |
| --- | --- | --- |
| `/quickstats/` | 86,400s (24h) | JSON serialized |
| `/browse/{field}/{val}` | 86,400s (24h) | JSON serialized |
| `/neuron/` | 86,400s (24h) | Pickle serialized |
| `/search/{keyword}` | 500,000s (~5.8 days) | Pickle serialized |
| `/metavals/` | 86,400s (24h) | JSON serialized |
| `/chartcount/{field}/{cutoff}` | 86,400s (24h) | JSON serialized |

### Cache invalidation

There is no per-key invalidation. The `/clear` endpoint flushes all Redis keys:

```bash
curl http://localhost:8002/clear
```

This clears the response cache, ID lists, search index, and any active shopping carts.

## ID List Chaining

Search and filter endpoints store their result neuron IDs in Redis so subsequent requests can filter within those results.

### Flow

1. Client calls `GET /search/cortex` or `GET /neuron/?species_name=rat`
2. The endpoint collects all matching neuron IDs into a Python list
3. The list is pickled and stored: `r.set(idlistkey, pickle.dumps(ids), ex=TTL)`
4. The `idlistkey` (a hash of the ID tuple) is returned in the paginated response
5. Client passes `idlistkey` to another endpoint: `GET /neuron/?idlistkey=xxx&gender=M`
6. That endpoint unpickles the ID list and adds it as a `.filter(id.in_(idlist))` clause

This enables chaining: search results can be further filtered by metadata, or browse results can be scoped to a previous search.

## Full-Text Search (RediSearch)

The search system uses [RediSearch](https://redis.io/docs/interact/search-and-query/), a Redis module for full-text indexing and querying.

### Index structure

- **Index name:** `nmo_idx`
- **Key prefix:** `nmo_kw:`
- **Schema:** Two text fields: `title` (neuron ID) and `body` (concatenated metadata)

### Building the index

Call `GET /feedsearch` to build or rebuild the index:

1. Drops the existing `nmo_idx` index (if any)
2. Creates a new index with the schema above
3. Reads all neuron metadata from PostgreSQL via `com.getdataforsearch()`
4. For each neuron, creates a hash key `nmo_kw:{id}` with `title` and `body` fields
5. The `body` field is a concatenation of species, region, cell type, archive, and other metadata text

### Querying

`GET /search/{keyword}` runs a RediSearch query:

```python
r.ft("nmo_idx").search(Query(keyword).paging(0, 100000))
```

Results are neuron IDs extracted from the `title` field of matching documents.

### When to rebuild

The search index must be rebuilt after:
- Importing new data
- Refreshing materialized views
- Any data change that affects neuron metadata

## Shopping Cart

Cart state is stored in Redis Sets, providing O(1) add/remove and automatic deduplication.

### Data model

Each cart has two keys:

- `cart:{uuid}` — a Redis **Set** containing neuron name strings. Created on first `SADD`.
- `cart:{uuid}:meta` — a Redis **String** with value `"1"`. Created immediately on cart creation. Distinguishes an empty cart from an expired/nonexistent one.

### TTL behavior

Both keys have a 24-hour TTL (86,400 seconds). The TTL is refreshed on every cart operation (view, add, remove, download), keeping active carts alive. After 24 hours of inactivity, the cart expires automatically.

### Operations and Redis commands

| API Operation | Redis Commands |
| --- | --- |
| Create cart | `SET cart:{uuid}:meta "1" EX 86400` |
| View cart | `EXISTS cart:{uuid}:meta`, `SMEMBERS cart:{uuid}`, `EXPIRE` on both keys |
| Add to cart | `SADD cart:{uuid} name1 name2 ...`, `SCARD` for count, `EXPIRE` on both keys |
| Remove from cart | `SREM cart:{uuid} name1 name2 ...`, `EXPIRE` on both keys |
| Clear cart | `DEL cart:{uuid} cart:{uuid}:meta` |
| Download cart | `SMEMBERS cart:{uuid}`, `EXPIRE` on both keys |
| Check hard limit | `SCARD cart:{uuid}`, `SISMEMBER` for dedup check |

### Size limits

Configurable via environment variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `CART_SOFT_LIMIT` | 1000 | Warning threshold — response includes a `warning` field |
| `CART_HARD_LIMIT` | 5000 | Hard cap — add requests that would exceed this are rejected |

### Memory footprint

Each cart stores neuron names as set members. With a hard cap of 5,000 neurons and average name length of ~20 characters, a full cart uses roughly 100-150 KB of Redis memory. With the 4 GB memory limit, Redis can hold tens of thousands of concurrent carts.

## Monitoring

### Check Redis connectivity

```bash
docker exec nmo-cache-1 redis-cli ping
# Expected: PONG
```

### View all keys

```bash
docker exec nmo-cache-1 redis-cli keys '*'
```

### Check memory usage

```bash
docker exec nmo-cache-1 redis-cli info memory
```

### Check search index info

```bash
docker exec nmo-cache-1 redis-cli FT.INFO nmo_idx
```

### List active carts

```bash
docker exec nmo-cache-1 redis-cli keys 'cart:*:meta'
```

### Inspect a specific cart

```bash
docker exec nmo-cache-1 redis-cli SMEMBERS 'cart:<uuid>'
docker exec nmo-cache-1 redis-cli SCARD 'cart:<uuid>'
docker exec nmo-cache-1 redis-cli TTL 'cart:<uuid>:meta'
```
